# PRD-016 — Brew PI control and predictive-runtime removal

Status: SOFTWARE COMPLETE — TARGET/PHYSICAL A/B PENDING — 2026-07-28

## Summary

Replace the current Brew nonlinear duty curve with a compile-time-selectable
proportional-integral controller using conditional anti-windup, while retaining
the existing ten-second SSR window and fixed Manual/main-extraction `+2°C`
heater-duty target bias. The build flag keeps the legacy curve authoritative
with PI running in shadow mode, or allows PI to command Brew heater duty for
controlled A/B testing. Steam control remains unchanged.

Remove the complete passive temperature-prediction runtime and its public/mobile
surface: firmware inference, configuration, snapshots, history fields, API v2
prediction query/payload, protocol schemas, simulator data, mobile polling and
persistence, CSV prediction columns, fixtures, and tests. Preserve PRD-012,
the predictive-temperature specifications, the desktop thermal-modeling tool,
and existing raw captures as historical/future research material.

## Goals

- Add a deterministic Brew PI controller with bounded output and conditional
  anti-windup.
- Select legacy-authoritative or PI-authoritative Brew control at build time so
  the owner can perform repeatable A/B tests through normal rebuild/reflash.
- Preserve the ten-second SSR window, 500 ms temperature schedule, heater
  safety lease, fail-off ownership, and every existing fault and timeout.
- Preserve the accepted fixed Manual/main `+2°C` duty-target bias as the first
  feed-forward mechanism while deferring measured-flow compensation.
- Replace unvalidated prediction data with compact controller diagnostics that
  make legacy, shadow-PI, and active-PI captures unambiguous.
- Remove passive prediction from firmware, protocol, simulator, mobile storage,
  polling, history synchronization, and new CSV exports.

## Non-Goals

- PID derivative control, runtime gain tuning, autotuning, runtime controller
  switching, NVS-persisted gains, or a mobile/API controller toggle.
- Changing Steam control, the fixed Steam temperature correction, readiness,
  heating/Steam timeouts, over-temperature thresholds, cooldown, or pump
  authority.
- Shortening the SSR window, adding a faster actuator task, pulse-density
  modulation, or increasing SSR switching frequency.
- Heater feed-forward from scale weight, app-derived flow, inferred inlet flow,
  pressure, or a new flow sensor.
- Activating ML, a temperature predictor, model export, or model coefficients
  on the ESP32.
- Deleting predictive-control documents, the desktop thermal-modeling
  implementation, existing modeling runs, or raw CSV captures.
- Treating simulator, host, build, or A/B software results as proof of physical
  heater output, de-energization, wiring, or mains safety.

## Context

PRD-012 added a passive fixed-coefficient predictor and explicitly kept it out
of the SSR command path. Evaluation of the collected captures found the
handwritten slope extrapolation useful at five seconds but unreliable near the
target at twenty seconds, while the correction uses the maximum 5/10/20-second
forecast. Keeping the unvalidated forecast in firmware, API history, mobile
storage, and CSV now consumes runtime and contract surface while producing data
that must not be mistaken for a validated model.

The authoritative Brew controller is still the nonlinear curve documented by
PRD-012: full heat outside a ramp band, a squared normal ramp, and a linear
recovery ramp in a ten-second time-proportional SSR window. It is not PID.
PRD-004 separately added the accepted fixed `+2°C` Manual/main-extraction bias
to the private heater-duty target. This PRD preserves that bias and every
PRD-004 safety boundary.

PRD-016 supersedes PRD-012 only as current runtime and public-contract behavior.
PRD-012 remains completed historical evidence. Its firmware prediction,
hypothetical correction, enriched prediction history, and mobile prediction
export are deliberately retired. The desktop specifications and tooling remain
available for a future, separately approved predictive-control initiative.

## Requirements

### Brew PI policy and build-time A/B selection

- Add `CONFIG_PHILCOINO_BREW_PI_CONTROL` as a build-time boolean. It must not be
  writable through HTTP, mobile state, profiles, NVS, or another runtime path.
- With the flag disabled, the existing nonlinear Brew curve remains the sole
  SSR-duty authority and PI runs in shadow mode without changing heater
  commands, readiness, timeouts, faults, or extraction behavior.
- With the flag enabled, PI supplies Brew requested duty to the existing
  ten-second heater window. The legacy curve remains calculation-only for A/B
  diagnostics and cannot modify the active PI command.
- Both builds must identify the authoritative controller as `legacy_curve` or
  `pi` in diagnostic history and CSV. Captures must also identify the firmware
  build, configured PI gains, filter configuration, and ten-second SSR window.
- Steam must continue using its current controller and compile-time `+5°C`
  active-temperature correction regardless of the Brew flag.

### PI calculation and state

- Calculate PI from a controller-owned filtered Brew temperature on the fixed
  500 ms temperature schedule:

  ```text
  error = private_brew_duty_target - filtered_temperature
  proportional = Kp * error
  integral = integral + error * dt
  requested_duty = clamp(proportional + Ki * integral, 0, 1)
  ```

- Use one compile-time Brew `Kp`/`Ki` gain set for warm-up, idle, extraction,
  and recovery in the first implementation. No derivative term may be hidden
  in the filter or duty adapter.
- Use conditional anti-windup: reject an integration step when output is
  saturated and the current error would drive it farther into saturation.
  Bounds and finite-value checks must prevent integral or output overflow.
- Reset PI filter/integral state on boot, Brew/Steam mode changes, active-target
  changes, controller reset, and fault dismissal. Fault, cooldown inhibit,
  target persistence, disabled heater permission, invalid sensor input, and
  failed output state must freeze or reset integration according to one tested
  deterministic policy and command the existing safe output path.
- Shadow PI must receive the same validated Brew temperature, private duty
  target, timing, extraction phase, and inhibition inputs that active PI would
  receive. Shadow state may not influence any authoritative state transition.
- PI gains and filter constants must remain compile-time firmware
  configuration. Initial values require offline/shadow evidence and explicit
  owner approval before an active-PI physical build is accepted.

### Extraction compensation and SSR actuation

- Retain the PRD-004 private duty-target calculation exactly: pre-infusion uses
  `0°C`, Manual/main extraction uses
  `min(brewTargetC + 2°C, brewOverTemperatureC - 1°C)`, and soak/idle use the
  base Brew target.
- With active PI, apply this private target only to PI error. It must not mutate
  persisted/API targets, readiness, heating deadlines, over-temperature
  thresholds, profile data, or Steam behavior.
- Preserve the ten-second time-proportional SSR window and existing minimum
  pulse policy for both A/B builds. Do not introduce a second heater-output
  timing owner.
- Extraction phase changes must retain their current heater-window reset
  behavior. Faults, over-temperature, invalid readings, cooldown, target
  transactions, disabled permission, safety-lease trips, and output failures
  must interrupt or suppress heater commands independently of requested duty.
- Record requested duty separately from the acknowledged Boolean heater command
  and recent delivered-command duty. Neither value may be described as measured
  SSR current or physical heater power.

### Predictive-runtime and contract removal

- Delete firmware prediction model/configuration, validation, EMA/slope/history
  feature generation owned only by prediction, forecasts, hypothetical
  correction, fallback state, snapshot fields, codec, history packing, target
  configuration, and prediction-specific host tests.
- Remove `GET /api/v2/state?include=prediction`,
  `MachineStateWithPredictionV2`, predictive history fields, prediction enums,
  schemas, OpenAPI components, fixtures, captures, and simulator behavior.
  Queryless API v2 and API v1 machine behavior must otherwise remain unchanged.
- Treat this as an intentional firmware/mobile API v2 compatibility break.
  Firmware and mobile from this PRD are deployed as a matched version; no
  backward prediction parser or compatibility payload is retained.
- Replace prediction-heavy history with bounded controller diagnostics:
  raw/filtered temperature, base/private target, error, selected controller,
  legacy requested duty, PI requested duty, proportional contribution,
  integral contribution/state, saturation/anti-windup state, acknowledged
  heater command/delivered-command duty, pump command, extraction phase, and
  controller operating mode.
- Rebaseline history entry size, ring capacity, page size, serialization
  capacity, stack, heap, and flash after removal/addition. The resulting
  diagnostics must not exceed the existing history memory budget or extend the
  500 ms temperature deadline.

### Mobile, CSV, desktop, and documentation

- Remove live prediction polling, prediction networking types, reducers/view
  models, debug data, local persistence, history synchronization, CSV columns,
  tests, and user-visible prediction state from the mobile application.
- Migrate existing local history by preserving ordinary temperature/control
  samples and discarding stored prediction values. New CSV export must contain
  the controller diagnostics above and no prediction, forecast, model version,
  feature schema, training hash, or hypothetical-correction columns.
- Preserve existing raw CSV files and modeling runs unchanged. Desktop
  ingestion may accept old prediction columns but must ignore them by default;
  the minimum non-predictive temperature/heater/pump inputs remain supported.
- Preserve the predictive firmware and desktop specifications, but mark the
  firmware integration path as deferred/historical and identify that no current
  firmware/API consumer exists. Keep PRD-012 unchanged as historical evidence.
- Align architecture, development, safety, tuning, protocol, README, side-note,
  and review documentation with the selected controller, removed prediction
  surface, A/B evidence boundary, and unchanged physical-safety limitations.

### Verification and physical acceptance

- Pure host tests must cover PI arithmetic, irregular/invalid timing, finite
  checks, conditional anti-windup in both saturation directions, reset/freeze
  transitions, target/mode/phase changes, extraction bias, and duty bounds.
- Trace-equivalence tests must prove that a flag-disabled build produces the
  same authoritative Brew and Steam heater commands as the legacy controller
  before this PRD, apart from deliberately removed diagnostics.
- Shadow tests must prove that arbitrary PI outputs cannot affect SSR commands,
  faults, readiness, timeouts, extraction, cooldown, persistence, or API state.
- Active-PI tests must prove that only Brew duty authority changes and that all
  existing fail-off paths dominate PI output.
- Run the affected OpenAPI/protocol, simulator, mobile tests/typecheck/lint,
  firmware host/sanitizer suite, resource checks, and pinned ESP-IDF target
  build. Simulator success is not thermal or heater-safety evidence.
- Physical A/B sessions require explicit authorization and supervision. Record
  exact build flag, firmware revision, gains, filter, target, extraction
  scenario, sensor/setup, independent cutoff, ambient/start conditions,
  requested/delivered command trace, and measured temperature outcome.
- Active PI is physically acceptable only after owner review demonstrates:
  at least 30% lower median warm-up/recovery overshoot, no more than 20%
  increased recovery time, stable idle without sustained oscillation, and no
  new heater fault, timeout, switching, deadline, or safety-lease regression.

## Implementation Overview

1. Change the authoritative contract first: remove prediction shapes/query and
   define bounded controller diagnostics, mobile migration, and new CSV shape.
2. Remove prediction runtime/configuration/history packing from firmware while
   retaining historical documents and desktop tooling.
3. Add the pure Brew PI policy, filter, conditional anti-windup, deterministic
   state transitions, compile-time gains, and build selector.
4. Integrate legacy-authoritative shadow PI and PI-authoritative Brew duty
   through the existing ten-second window and fail-off path.
5. Align simulator, mobile history/persistence/export, protocol fixtures,
   documentation, and resource budgets.
6. Complete automated and target evidence, then perform separately authorized
   supervised A/B sessions before accepting active PI.

## Open Questions

- Initial `Kp`, `Ki`, filter constant, and integral bounds are execution outputs
  of shadow analysis and supervised tuning, not pre-approved values.
- A shorter SSR window, derivative term, measured-flow feed-forward, runtime
  tuning, or predictive firmware requires a later separately approved PRD.

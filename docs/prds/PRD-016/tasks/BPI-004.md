# BPI-004 — Integrate Brew PI shadow and active authority

Status: Done
Review Mode: Agent
Review Reason: Build-flag ownership, trace equivalence, Steam preservation, and
fail-off dominance can be proven through deterministic controller/output fakes.

## Goal

Integrate PI into the existing temperature controller so a disabled build keeps
legacy Brew duty authoritative with shadow PI, while an enabled build makes PI
the sole Brew requested-duty authority through the existing SSR window.

## Scope

- Feed shadow and active PI the same validated Brew temperature, private duty
  target, fixed timing, extraction phase, and inhibition state.
- Keep the ten-second SSR window, minimum pulse policy, window reset behavior,
  heater lease, output owner, faults, timeouts, cooldown, permission, and target
  transaction boundaries.
- Preserve the exact Manual/main bounded `+2°C` private duty-target bias,
  pre-infusion `0°C`, and base target during soak/idle.
- Keep Steam control and its compile-time `+5°C` active-temperature correction
  unchanged under both builds.
- Publish selected controller and separate requested/acknowledged/delivered
  command diagnostics.

## Non-Scope

- Flow compensation, runtime switching/tuning, new output timing, Steam PI,
  physical A/B acceptance, or changes to independent safety mechanisms.

## Implementation Plan

1. Characterize pre-PRD legacy Brew and Steam command traces.
2. Run legacy and PI calculations side by side for Brew diagnostics.
3. Select exactly one requested-duty authority at compile time.
4. Route the selected duty through the existing heater window and fail-off
   output path.
5. Add flag-disabled equivalence, shadow isolation, active-PI ownership, bias,
   phase reset, and every fail-off dominance regression.

## Acceptance Criteria

- [x] Disabled flag produces legacy-authoritative Brew and unchanged Steam
  heater-command traces apart from removed/replaced diagnostics.
- [x] Arbitrary shadow PI output cannot alter SSR commands, readiness, faults,
  timeouts, extraction, cooldown, persistence, or ordinary API state.
- [x] Enabled flag changes only Brew requested-duty authority.
- [x] Manual/main applies the bounded `+2°C` private target only to controller
  error; pre-infusion/soak/idle semantics remain exact.
- [x] Invalid readings, faults, target transactions, cooldown, permission,
  safety lease, and output failures dominate any PI request.
- [x] Native/sanitizer controller and integration tests pass in both flag modes.

## Completion Evidence

- Default/disabled builds retain the exact legacy pulse calculation as Brew
  authority while PI runs in shadow; enabled test builds route only Brew PI
  requested duty through the existing window/minimum-pulse/output owner.
- Steam stays on the legacy controller and retains the fixed `+5°C` correction.
- Separate legacy and active-PI authority executables cover arbitrary shadow
  outputs, bias/phase changes, target transactions, cooldown, permission,
  invalid sensor, output failure, and fault dismissal/reset.
- PASS — native and configured sanitizer matrices 10/10; 32 strict captures.
- Detailed evidence: `../evidence/FIRMWARE-IMPLEMENTATION.md`.

## Verification Strategy

- Build and run host suites with the selector disabled and enabled.
- Compare deterministic legacy traces, inject arbitrary PI results in shadow,
  and inject all existing safety/fail-off transitions in active mode.

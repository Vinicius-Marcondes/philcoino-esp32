# PRD-013 — ESP32-C3 firmware performance and lean runtime

Status: APPROVED — 2026-07-26

## Summary

Reduce avoidable ESP32-C3 work, shared-mutex exposure, API allocation pressure,
and firmware maintenance surface without changing the machine's public
contract or control authority. Keep the scale ready for immediate one-tap
automatic tare, but replace unconditional idle polling with event-driven
acquisition. Remove the already-disabled OLED implementation completely.

## Goals

- Make temperature, extraction, scale, and API timing more deterministic on the
  ESP32-C3's single CPU.
- Reduce idle scale wakeups, repeated scale calculations, workflow-mutex
  contention, and avoidable HTTP allocations.
- Keep state reads observational and move scale-calibration NVS commits outside
  the real-time synchronization boundary.
- Establish before/after target evidence for CPU, timing, heap, stack, flash,
  API latency, interrupts, and safety-lease behavior.
- Remove OLED support and verified abandoned code while retaining active
  profiles, history, scale, prediction, and API compatibility.

## Non-Goals

- Changing OpenAPI, API v1/v2 wire shapes, authentication, or polling semantics
  outside the identified mobile scale-polling defect.
- Removing or reducing firmware profiles, ten-minute history, passive
  prediction, HX711 support, heater or pump policies, timeouts, faults, or
  fail-off behavior.
- Changing task priorities without target evidence, broadly rewriting the API
  codec, or adding a public diagnostics endpoint.
- Reintroducing a second temperature sensor or removing documentation of the
  current single-sensor safety limitation.
- Flashing, energized mains testing, hardware approval, PID changes, or active
  predictive temperature control.

## Context

The scale task currently wakes every 10 ms and enters the shared workflow mutex
even when the HX711 reports no ready sample. The workflow also recomputes scale
stability and median data at 100 Hz. Mobile can unintentionally poll the scale
endpoint every 250 ms while idle because its polling callback retains stale
scale state.

API v2 state reads currently advance workflow state even though a dedicated
10 ms task owns extraction and cooldown updates. Some API routes also retain the
shared mutex through heap-backed JSON serialization. Scale calibration performs
a synchronous NVS commit while holding that same boundary.

OLED execution is disabled, but its renderer, framebuffer, I2C transport,
configuration, dependency, tests, and stale documentation remain. The earlier
dual-temperature-sensor runtime has already been removed. Firmware profile
storage is active: it owns profile timing, synchronization, and weighted
extraction, so it is not a ghost feature.

## Requirements

- Record an unchanged-code target baseline before optimization and repeat the
  same scenarios afterward. Diagnostics must use bounded storage, avoid hot-path
  logging, default off, and add no public API.
- Keep Dashboard polling completion-driven and non-overlapping. Poll scale at
  one-second cadence while idle and 250 ms only while the Scale page is visible
  or weighted extraction is active.
- Make API state reads snapshot-only. Only the dedicated workflow task may
  advance extraction, cooldown, scale settling, or the extraction phase used by
  temperature control.
- Copy coherent controller snapshots under the workflow mutex, then release it
  before serialization and HTTP response construction. Remove known duplicate
  route/header work and reserve bounded response capacity without a wholesale
  codec rewrite.
- Wake the scale task through an HX711 data-ready GPIO notification. The ISR may
  only notify the task; GPIO clocking, filtering, logging, and controller
  publication remain task-owned. A bounded timeout must still detect an
  unavailable scale.
- Never acquire the workflow mutex for `NotReady`. Recompute the rolling median,
  spread, stability, and calibrated weight only after an accepted sample and
  expose cached O(1) snapshots with current age and availability.
- Preserve a ready scale window for immediate automatic tare and continue
  sampling through the existing bounded post-extraction settling interval.
- Complete scale calibration through prepare, unlock, NVS save, relock, and
  adopt phases. Save failure retains the previous calibration and allows retry.
  Reacquisition or adoption failure must block weighted Start until recovery.
- Run the temperature loop on a fixed 500 ms `vTaskDelayUntil` period. Preserve
  current priorities unless a later approved change is justified by target
  evidence.
- Preserve the cache-safe GPTimer heater-lease ISR. Do not add logging,
  allocation, controller work, or broad interrupt-disabled regions to either
  application ISR.
- Remove all OLED source, configuration, tests, ESP-IDF I2C dependency, startup
  branches, and current-hardware claims. GPIO8 and GPIO9 become unassigned.
- Remove only production-unreachable helpers confirmed by call-graph review.
  Preserve historical and safety documentation where it still explains a
  decision or limitation.
- Keep software verification separate from connected-target Human acceptance
  and from any energized physical-safety claim.

## Implementation Overview

1. **PERF-001 — Baseline and instrumentation:** capture fixed-allocation
   before-change resource, latency, loop-jitter, mutex, stack, reset, and
   safety-lease evidence.
2. **PERF-002 — Mobile API consumption:** correct stale scale-polling state and
   prove bounded completion-driven idle and active request rates.
3. **PERF-003 — Read-only live-state export:** make API v2 state observational
   and leave all workflow advancement to its dedicated task.
4. **PERF-004 — API lock and allocation containment:** snapshot under lock,
   serialize after unlock, and remove bounded avoidable route/header/response
   allocations.
5. **PERF-005 — Event-driven HX711 acquisition:** add data-ready task
   notification, timeout detection, and no-publication handling for `NotReady`.
6. **PERF-006 — Cached scale processing:** update derived scale state only for
   accepted samples and make consumer snapshots O(1).
7. **PERF-007 — Transactional calibration persistence:** move NVS outside the
   mutex with explicit prepare, adopt, retry, and fail-safe blocking states.
8. **PERF-008 — Deterministic loop scheduling:** adopt fixed-period temperature
   scheduling and bounded lateness measurement without changing priorities.
9. **PERF-009 — Interrupt safety and timing:** validate the new HX711 notifier,
   existing heater lease, and HX711 clock pulses under target load.
10. **PERF-010 — OLED removal:** delete display behavior, transport, dependency,
    configuration, tests, and stale current-state documentation.
11. **PERF-011 — Ghost-feature cleanup:** remove verified unreachable helpers,
    confirm the dual-sensor runtime is absent, and preserve active features.
12. **PERF-012 — Regression and target evidence:** run the complete verification
    matrix, publish before/after results, and retain the Human acceptance gate.

Task files and tracker entries were created through the supervised task
workflow after explicit owner approval on 2026-07-26.

## Acceptance Criteria

- [ ] Idle or disconnected scale operation no longer causes 100 workflow-mutex
  acquisitions per second, while automatic tare still uses a fresh stable
  window before the pump starts.
- [ ] Mobile scale polling is non-overlapping and bounded to approximately one
  request per second while idle and four only in the approved fast states.
- [ ] Repeated API v2 state reads cannot advance workflows or alter acknowledged
  pump, heater, cooldown, extraction, or scale-settling state.
- [ ] API v1 state, API v2 state, scale, extraction, cooldown, and profile
  responses serialize after releasing the workflow mutex.
- [ ] Calibration NVS I/O never occurs under the workflow mutex; save,
  reacquisition, and adoption failures preserve deterministic fail-safe
  behavior and are covered by tests.
- [ ] HX711 ready-before-wait, notification coalescing, timeout, disconnect,
  saturation, recovery, calibration, tare, cutoff, fallback, and settling paths
  are deterministic in host and target evidence.
- [ ] Temperature scheduling remains fixed-period under idle, heating, timed and
  weighted extraction, calibration commit, API/history load, Wi-Fi reconnect,
  and mDNS degradation.
- [ ] OLED symbols, configuration, startup branches, tests, and `esp_driver_i2c`
  are absent; GPIO8/GPIO9 are unassigned and the target image is smaller than
  the recorded baseline.
- [ ] Existing protocol, simulator, mobile, firmware host/sanitizer, and
  available target-build checks pass without profile, history, prediction,
  extraction, cooldown, heater, pump, or fault regressions.
- [ ] Connected-target evidence reports CPU/timing, mutex wait/hold, heap,
  largest free block, stack high-water, flash, API latency, GPIO timing, reset
  causes, and lease trips with zero watchdog resets, unexpected lease trips,
  control deadline failures, or output-state regressions.
- [ ] Connected-target runtime and logic-analyzer results receive separate Human
  acceptance; no automated result is presented as energized mains approval.

## Open Questions

- No product decision remains open. Exact performance deltas must come from the
  PERF-001 baseline and PERF-012 repeat rather than source-level estimates.

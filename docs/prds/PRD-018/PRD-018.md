# PRD-018 — Dynamic Steam heat-soak compensation

Status: Approved / Finished

Approved: 2026-07-30

## Summary

Compensate for the observed delay between hot steam at the top of the boiler
and the lateral thermocouple reaching thermal equilibrium. On entry to Steam,
firmware adds a configurable transient estimate to the globally calibrated
sensor reading. The estimate decays linearly to zero and is used for Steam
control, readiness, heating demand, recovery, duty, status, and timeout start.

The calibrated thermocouple value remains the public sensor reading. The
transient estimate is exposed separately and does not alter either the raw or
calibrated `135°C` over-temperature check.

## Product Decisions

- Default initial compensation: `12°C`; configurable `0–20°C` in whole degrees.
- Default linear decay: `12 minutes`; configurable `1–30 minutes` in whole
  minutes.
- Default post-ready Steam timeout: `5 minutes`; configurable `1–15 minutes`
  in whole minutes.
- A heat-soak episode starts on Steam entry. It survives temporary mode changes
  and ends only after the machine is outside Steam and the calibrated
  temperature reaches the Brew target or below.
- The episode is volatile across reboot. Settings are persisted in a dedicated
  versioned NVS record.
- Missing settings initialize and persist the defaults. Corrupt, unreadable, or
  unsavable storage follows the firmware fail-off boundary.
- Settings may change in any non-fault state. Firmware commands the heater off
  before persistence and does not restart an active heat-soak or ready-timeout
  origin.
- Shortening an active ready timeout takes effect from its original ready
  timestamp and may return the machine to Brew on the next control update.
- API compatibility with a client that predates this required state field is
  intentionally not retained.

## Safety Boundary

- `boilerTemperatureC` remains the globally calibrated lateral thermocouple
  reading.
- `steamControl.controlTemperatureC` is a control estimate, not a second sensor
  or a measured top-of-boiler temperature.
- Raw and calibrated Steam readings are each permitted through exactly
  `135°C`; either strictly above the cap independently latches
  `over_temperature`.
- Sensor validation, heating timeout, SSR safety lease, manual permission,
  faults, boot-off ordering, and independent physical protection are unchanged.
- Software and simulator evidence do not validate the reported `10–15°C` gap,
  prove equilibrium time, establish safe energized tuning, or confirm physical
  heater interruption.

## Acceptance Criteria

- [x] Strict protocol settings/state schemas and authenticated GET/PATCH routes
  cover all ranges and reject empty, fractional, stepped, extra, or out-of-range
  mutations.
- [x] Firmware applies one wrap-safe linear transient only to Steam control
  semantics while leaving raw/calibrated safety checks unchanged.
- [x] Settings persist atomically outside the API lock and force heater output
  off before storage.
- [x] Heat-soak and ready-timeout origins survive active setting changes.
- [x] Simulator time, settings persistence, reset/power-cycle behavior, history,
  and injected persistence failures are deterministic.
- [x] Mobile presents the Steam estimate as primary in Steam, keeps the sensor
  reading visible, provides a focused settings screen, and exports the full
  context in retained history CSV.
- [x] All configured protocol, simulator, mobile, firmware host/sanitizer, and
  available pinned target checks pass.
- [ ] Instrumented, supervised physical runs establish appropriate production
  values and verify the independent cutoff.

For every candidate tuning run, retain the exact firmware build, settings,
global calibration, ambient/start conditions, lateral sensor trace, independent
top/boiler reference trace, heater-command trace, time to usable steam, time to
